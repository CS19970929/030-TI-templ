# 串口通信恢复与复用说明

## 1. 背景

本次调整的目标有两个：

1. 恢复当前项目的串口通信应答，保证原有 Modbus 通讯和新增 P12 协议都能继续按旧时序工作。
2. 在不改变当前串口行为的前提下，收敛 `SCI1` / `SCI2` 的重复代码，方便移植到同类旧项目。

## 2. 问题复盘

上一轮改动把发送链路改成了 `TXE/TC` 中断发送，同时补了超时和异常恢复。该方案从结构上是可行的，但对当前旧项目来说改动过大，直接改变了以下关键时序：

1. 发送从原来的主循环轮询发送，变成了中断驱动发送。
2. 接收关闭、发送启动、发送完成后的状态切换路径发生变化。
3. `USARTx_IRQHandler` 的处理入口从单一 `RXNE` 扩展到了 `RXNE/TXE/TC`。

这类项目的串口状态机本身比较脆弱，虽然逻辑上看是“增强”，但现场更依赖原始实现的时序细节，所以会出现“通讯不上、不应答”。

## 3. 本次修复原则

本次不继续保留发送中断化实现，而是采用“恢复稳定行为 + 做等价重构”的方式：

1. 恢复到 `b65c6b7` 版本可工作的发送/接收时序。
2. 保留新增的 P12 协议接入能力。
3. 仅抽取公共 helper，减少 `SCI1` / `SCI2` 重复，不改变外部接口、不改变协议时序、不改变主循环调用关系。

## 4. 实现结果

### 4.1 通讯行为恢复

以下行为恢复为原有实现：

1. 发送仍然使用主循环中的轮询发送，不使用 `TXE/TC` 发送中断。
2. `USART1_IRQHandler` / `USART2_IRQHandler` 仅在 `RXNE` 触发时进入接收处理。
3. 完整帧接收后仍按原方式关闭接收，发送完成后再恢复接收。
4. 保留原长帧发送节流逻辑：发送到第 `19/39/59` 字节后，继续按旧代码插入延时。

### 4.2 架构复用

在 `Sci_Upper.c` 内新增了以下公共静态函数：

1. `Sci_CommonUpper_FaultChk`
2. `Sci_CommonUpper_Rx_Deal`
3. `Sci_CommonUpper_Tx_Deal`
4. `App_CommonUpperSCI`

`SCI1` / `SCI2` 现在只保留薄包装函数：

1. 串口实例不同
2. 错误计数、发送标志不同
3. 其余收包、组包、发送状态机逻辑共用同一份实现

这样做的好处是：

1. 移植到旧项目时，只需要复制一套公共 helper。
2. 新项目如果只有一个串口，也可以直接保留一层包装，不必删改业务逻辑。
3. 后续若再增加 `SCI3` 或其他 UART 口，复用成本会明显降低。

## 5. 迁移到其他旧项目的建议方式

如果其他旧项目也是当前这种架构，建议按下面顺序迁移：

1. 先迁移 `P12_Protocol.c/.h`。
2. 再迁移 `Sci_Upper.c/.h` 中的协议识别和公共 helper。
3. 最后适配目标项目的 `USARTx_IRQHandler`，保持“只在 `RXNE` 中进入接收处理”的模式。

迁移时重点确认：

1. 目标项目的串口波特率、校验位、停止位配置是否与当前项目一致。
2. 目标项目的 `RS485_SLAVE_ADDR`、广播地址、寄存器定义是否一致。
3. 目标项目是否也依赖长包发送时的 10ms 节流逻辑。
4. 目标项目是否已经有自己的错误计数和发送完成标志位。

## 6. 为什么这次不继续保留“发送中断版”

不是发送中断方案一定不对，而是它不适合直接硬切到这类旧项目中。对这类项目，更稳妥的路线是：

1. 先保持原有时序不变，把协议功能接进去。
2. 再做重复代码收敛。
3. 最后如果要继续做发送中断化、超时恢复、异常自恢复，应该单独立项，结合实机联调逐步切换，而不是一次性替换。
