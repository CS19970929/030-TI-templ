# 串口通信改造需求与实现说明

## 当前需求整理

本轮改造目标有四个：

1. 在当前 `Sci_Upper` 架构基础上接入 P12 协议，不影响现有 Modbus/寄存器协议功能。
2. 优化当前串口链路实现，解决阻塞发送、异常恢复不足、缺少超时机制的问题。
3. 结构上保持对旧项目友好，便于把同类改动迁移到其他仍采用 `Sci_Upper + 串口中断 + 主循环状态机` 的旧工程。
4. 产出可交付文档，并形成清晰提交记录。

## 约束与边界

- 不能破坏现有 `0x03/0x06/0x10` 协议行为。
- 尽量不改动上层业务模块调用关系。
- 保持旧项目可复用，因此改动尽量收敛在：
  - `Sci_Upper.c`
  - `Sci_Upper.h`
  - `stm32f0xx_it.c`
  - 新增协议模块

## 原实现存在的问题

### 1. 发送为阻塞轮询

旧实现由主循环调用 `Sci*_CommonUpper_Tx_Deal()`，内部轮询 `TXE` 并逐字节发送。问题：

- 占用主循环时间片
- 收发耦合较重
- 发送期间接收关闭时间偏长
- 长包或后续扩展协议时鲁棒性差

### 2. 错误处理中断恢复能力不足

旧实现虽然有 `FaultChk()`，但主要作用是：

- 清硬件错误位
- 增加错误计数

没有完成“丢弃半帧并恢复接收状态”的闭环。

### 3. 缺少接收超时

旧实现只有“按长度收满一帧”的完成条件，没有：

- 字节间超时
- 半包恢复

现场出现丢字节或噪声时，容易把后续字节继续拼到旧帧里。

## 本次实现内容

## 1. P12 协议并行接入

- 新增 `P12_Protocol.c/.h`
- 在 `Sci_Upper` 接收状态机中增加帧类型识别
- `0x21 0xAA` 走 P12 协议
- 原 `RS485_SLAVE_ADDR / RS485_BROADCAST_ADDR` 继续走旧 Modbus 逻辑

已实现命令：

- `0x80 -> 0x81`
- `0x82 -> 0x83`

## 2. 发送改为中断驱动

当前改为：

- 主循环只负责组帧并调用发送启动
- `USART TXE` 中断负责逐字节装载发送数据
- `USART TC` 中断负责判定整个报文物理发送完成

这样做的收益：

- 主循环不再阻塞等待串口发送
- 更适合迁移到旧项目
- 后续新增协议时不需要重新改发送框架

## 3. 保留原有长包节流行为

旧实现存在在第 `19/39/59` 字节后插入延时的行为。考虑到旧项目和旧上位机可能依赖该时序，本次没有删除，而是迁移到新的发送中断框架中继续保留。

## 4. 增加接收超时

在 `RS485MSG` 中增加：

- `u8RxTimeoutTick`

策略：

- 当串口处于接收半帧状态但长时间未继续收到字节时，自动丢弃当前帧
- 当前以 `10ms` 为基准计数
- 超时阈值为 `3` 个节拍

这部分逻辑也适合直接迁移到旧工程。

## 5. 增加异常自动恢复

在 `FaultChk()` 中，发现硬件串口错误后不再只计数，而是执行统一恢复：

- 停止发送中断
- 清空当前帧状态
- 重新使能接收

这样现场噪声或半包异常后，不需要依赖外部再次初始化串口。

## 6. 为旧项目迁移保留的结构设计

本次没有把通信层改造成大面积新架构，而是保留旧项目常见模式：

- 中断里逐字节收包
- 主循环里处理协议业务
- 发送由串口中断完成
- 异常和超时在 `Sci_Upper` 层内闭合

因此迁移时通常只需要：

1. 复制 `P12_Protocol.c/.h`
2. 合并 `Sci_Upper.h` 的结构字段
3. 合并 `Sci_Upper.c` 的公共收发增强逻辑
4. 修改对应 MCU 的 `USARTx_IRQHandler`

## 风险说明

### 1. 波特率

为了不影响当前项目已有通信，本次仍保留项目当前串口配置，不把物理层强制改成协议文档中的 `115200 8N1`。

### 2. 超时阈值

当前超时阈值偏保守，目的是兼容旧项目。若后续现场设备响应节拍明确，可再按项目串口速率单独细调。

### 3. 状态机仍是单缓冲

当前仍然是一份收发缓冲，不是双缓冲或 DMA 环形缓冲。对于本项目和同类旧项目这是可接受的，但如果后续协议吞吐量明显上升，建议再演进。

## 结论

本次改造已经完成以下闭环：

- P12 协议新增
- 原协议兼容保留
- 发送中断化
- 接收超时
- 异常自动恢复
- 旧项目可迁移设计

如果后续继续演进，推荐优先级为：

1. 抽离 `USARTx` 差异，做成单文件模板
2. 把 `Modbus` 和 `P12` 的分发进一步下沉成独立协议表
3. 若吞吐继续提升，再考虑 DMA 接收
